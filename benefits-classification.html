B.1.5 福利制度 － 福利代碼分類規則

後端 API 提供「名稱／分類／順序／是否法定」，前端一律照後端顯示；唯一前端特殊規則為法定項目獨立成第一分類。

一、需求解讀

現況問題 tCodeBenefit 表自帶的分類欄位「沒有在用」（見代碼表 §6 開頭註記），前端各專案自己 hardcode 名稱與分類 → 求才、求職、公司頁三邊顯示不一致，改一個字要動三邊程式。
後端要做 福利代碼 API 改為回傳完整顯示資訊：code（代碼）、name（新名稱，以 Google Sheet 版為準）、categoryId / categoryName（分類）、sort（分類順序與項目順序）、isStatutory（是否法定項目）。分類定義由後端維護，新增／異動代碼時一併給定分類與法定旗標。
前端要做 完全不再 hardcode：分類區塊、區塊標題、Chip 文字、排序全部照 API 給的走。
唯一的例外規則：isStatutory = true 的代碼，抽出來放在畫面第一個分類「法定項目」。
名詞對照：「新名稱」= 代碼表「名稱（新，Google Sheet）」欄；「舊名稱」= 現版文件用字（例：1102 舊「年節獎金」→ 新「年節獎金／禮品」、1303 舊「員工團保」→ 新「員工團體保險」）。API 只給新名稱，舊名稱不再出現在前端。

三、建議的 API 回傳格式

GET /api/company/benefit-codes        // 代碼字典（可全站快取）

{
  "categories": [
    { "id": "STATUTORY", "name": "法定項目", "sort": 1 },   // 由 isStatutory 聚合而成的虛擬分類
    { "id": "BONUS",     "name": "獎金類",   "sort": 2 },
    { "id": "LEAVE",     "name": "休假類",   "sort": 3 },
    { "id": "INSURANCE", "name": "保險類",   "sort": 4 },
    { "id": "MEAL",      "name": "餐飲類",   "sort": 5 },
    { "id": "HOUSING",   "name": "居住類",   "sort": 6 },
    { "id": "TRAFFIC",   "name": "交通類",   "sort": 7 },
    { "id": "FACILITY",  "name": "設備類",   "sort": 8 },
    { "id": "LEISURE",   "name": "娛樂類",   "sort": 9 },
    { "id": "SUBSIDY",   "name": "補助類",   "sort": 10 },
    { "id": "OTHER",     "name": "其他類",   "sort": 11 }
  ],
  "benefits": [
    {
      "code": 1001,
      "name": "勞保",                  // 新名稱，前端直接顯示
      "categoryId": "OTHER",
      "categoryName": "其他類",
      "sort": 1,
      "isStatutory": true,             // 前端唯一特殊規則的依據
      "requireSubmit": true,           // 送出前強制校驗（勞保、健保）
      "requireCheckAlert": true        // 未勾選要列入提示 Modal（1007／1702 為 false）
    }
  ]
}

GET /api/company/welfare              // 該廠商已勾選的代碼
{ "selectedCodes": [1001, 1002, 1105], "memo": "補充說明文字…" }
為什麼「法定項目」要當成 categories 的一員：這樣前端渲染邏輯完全統一 ——「依 sort 跑 categories，每個分類撈屬於它的 benefits」，不需要為法定項目寫第二套排版程式。後端只要把 isStatutory=true 的項目在組裝時歸到 STATUTORY 群即可。
這也和 104 的做法一致（104 代碼表本身就把勞保、健保、產假、哺乳室、週休二日…直接歸類為「法定項目」分類）。

四、待確認：法定項目要不要在原分類重複出現？

「額外顯示於第一分類」聽起來是複製一份，「獨立顯示」聽起來是抽出來。兩種解讀畫面差很多，下方 Demo 可切換比較。
方案畫面優缺點
A. 抽出（建議） 法定項目只出現在第一分類；休假類只剩生日假／旅遊假／不用補班，保險類只剩意外險… ✅ 同一代碼只有一個 Chip，勾選狀態不會有同步問題
✅ 與 104 分類方式一致
✅ 與現行 B.1.5 文件章節結構一致（§2 法定項目、§3~11 其他福利代碼）
B. 重複顯示 法定項目同時出現在第一分類與原分類 ⚠️ 同代碼兩個 Chip，勾其一另一個要連動
⚠️ 使用者容易誤以為是兩個不同項目
✅ 依分類找項目時不會「找不到特別休假」

建議採 方案 A。若最後採 B，前端須以 code 為唯一 key 共用勾選狀態（Demo 已實作連動）。

五、必須保留的既有規則（B.1.5 原文）

時機規則
初始化判斷廠商屬性 organs.confirmed & 131072（不可修改，廠商層級非帳號權限）：外網且有此旗標時顯示 Alert「不好意思，您目前沒有權限使用本功能，請聯繫客服人員。」並將送出按鈕設為 disabled。
初始化撈取廠商目前福利代碼，有代碼者 Chip 呈現 selected；Chip 需有 hover / selected / hoverselected 樣式。
初始化若有法定項目未勾選 → 顯示提示 Modal，列出未勾選的 15 項。
送出前強制校驗：勞保（1001）、健保（1002）必須已勾選。
送出時再檢查一次法定項目未勾選情境；Modal 文案：「刊登職缺須符合個人資料保護法、就業服務法、依法參加社會保險(勞保、職災保險、就保等)及勞退新制與相關法令。您尚未勾選：項目名稱」。確定 → 關 Modal 並送出；取消 → 關 Modal 返回。
兩處 Modal勾「我已了解相關規範，今日不再顯示」+ 確定 → localStorage 記錄 by 廠商 + by 帳號 的不顯示紀錄，效期一天，登出不清除。
補充說明資料來源 organs，textarea 上限 5000 字，即時正字與敏感字偵測，違反就服法／性平法字眼與競品字眼各有對應 error message。
新舊規則銜接：上面所有「法定項目」判斷，改為讀 API 的 isStatutory / requireSubmit / requireCheckAlert，前端不再維護任何代碼清單。
